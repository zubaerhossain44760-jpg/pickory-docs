3. SSR & Query Execution Engine

The Server-Side Rendering (SSR) and Query Execution Engine intercepts WooCommerce product queries during initial catalog page load and REST retrieval. Powered by PPFX_Server_Filter, PPFX_Product_Query_Builder, and PPFX_Query_Clause_Compiler, the subsystem safely modifies the main WP_Query loop before DOM output, eliminating Cumulative Layout Shift (CLS), preventing catalog 404 routing anomalies, and executing scoped, high-performance database queries with zero wp_postmeta joins.

4.2 QUERY INTERCEPTION

pre_get_posts & modify_main_query Interception

Modifying WordPress queries globally is hazardous. To avoid polluting secondary loops (menus, sidebars, related products) or backend admin tables, modify_main_query($query) enforces strict boundary guards:

PRIMARY LOOP GUARD

is_main_query() && !is_admin()

Immediately bails if the query is not the primary WordPress loop or is executing in an administrative context. Secondary product sliders and footer widgets remain completely untouched.

CATALOG ARCHIVE CONTEXT

Archive Detection Heuristic

Verifies the current request matches is_shop(), is_product_category(), is_product_tag(), or a custom product taxonomy archive (e.g. brand, designer).

TAXONOMY INHERITANCE

Archive Context Merging

When filtering on /product-category/shoes/, the queried term is automatically extracted and merged into active parameters, ensuring filters operate strictly within the scoped category.

4.3 ROUTING DEFENSE

Shop 404 & Redirect Guard

Faceted filtering in WordPress introduces severe URL routing conflicts due to core's rewrite engine:

[CORE REWRITE ANOMALY]

The Taxonomy 404 Collision

WordPress core registers rewrite query vars for taxonomy slugs (e.g. product_tag). When a filtered URL like /shop/?product_tag=summer is requested, WordPress attempts to parse the shop page with a taxonomy constraint. If the taxonomy constraint does not resolve to the configured shop page ID, WordPress core emits an HTTP 404 header before WooCommerce template loading begins.

Pickory eliminates this via normalize_shop_request_query_vars($query_vars):

  • Intercepts the raw request query vars at Priority 1.
  • Detects if the query targets the configured shop page.
  • Removes conflicting taxonomy query parameters from the WordPress internal query parser, keeping $_GET intact for Pickory.
  • prevent_canonical_redirect() inspects incoming GET parameters; if any key starts with ppfx_, it returns false to prevent WordPress from stripping parameters and redirecting to the canonical shop root.

4.6 SCOPED HOOK LIFECYCLE

Scoped posts_clauses Hooks & spl_object_hash Lifecycle

Standard WordPress SQL filters (posts_clauses, posts_join, posts_where) are global singletons. Once added via add_filter(), they execute on every subsequent query unless explicitly removed.

PPFX_Query_Hook_Scope solves this with an isolated object-hash lifecycle:

  1. When attach($query) is invoked, it records the unique memory identity of the target query via spl_object_hash($query).
  2. In the attached SQL callback, it inspects the passing query: 
    if ( spl_object_hash( $wp_query ) !== $this->expected_hash || ! $wp_query->get( 'ppfx_is_filter_query' ) ) {
    return $clauses;
}
  3. Hooks a cleanup listener on the_posts or posts_results that automatically detaches the exact callbacks as soon as the target query finishes executing.
  4. Guarantees zero leakage into secondary loop queries, navigation menus, or admin queries.
4.7 PERFORMANCE FIDELITY

Client-Server SSR Hash Parity

When a user loads a filtered URL (e.g. from a shared link or bookmark), the server renders the complete filtered catalog via SSR. Without state parity coordination, frontend JavaScript initializes, notices the active URL parameters, and immediately fires a redundant AJAX fetch—wasting bandwidth and causing layout flicker.

SERVER FINGERPRINT

ppfxFilterData.ssrHash

During SSR rendering, PPFX_Server_Filter normalizes the active parameters, sorts their keys alphabetically, and computes an MD5 checksum injected into the localized script global.

CLIENT VERIFICATION

Zero Redundant Fetch

On client boot, src/js/utils/hash.js computes the identical MD5 checksum of the current URL parameters. If clientHash === serverHash, the initial AJAX request is suppressed and DOM hydration completes instantly.
